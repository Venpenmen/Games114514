## P0 规则审查结果

### 已确认并可用作引擎输入

- 人数 4～11，固定人数房间；奇数浪人；每轮身份重置。
- 忍者牌 33：密探/隐士/盲眼刺客/上忍各六张，分别编号 1～6；六名骗徒 1～6；镜僧、殉道者、首脑各一。轮抽按 3 选 1 → 左传 2 → 选 1 → 弃 1。
- 五阶段出牌同时亮出，按编号执行；镜僧/殉道者为反应，首脑为揭示。规则书和官方 FAQ 支持掘墓人得到其他阶段牌可立即使用，或保存至合法时机。
- 荣誉数字版**推定**池 35 枚：2 分 14、3 分 14、4 分 7。原版未证实正式 35 枚的具体分布，必须清楚标注为数字版选择；补池用同配置。
- 既定计时默认：轮抽 45s、亮牌 30s、技能目标 30s、反应 15s、轮间准备 30s；游戏全离线时冻结剩余时间。
- 私人信息按取得时的事实记录快照，变形后的旧情报不更新；重连不增加私人权限。

### 原版技能 / 数字版结算的关键纠错

1. **掘墓人「立即使用」不等于无条件触发特殊牌。** 官方 FAQ 确认可以立即使用所取上忍牌，但镜僧/殉道者是受攻击时的 react、首脑在 reveal 且存活时触发。建议特殊牌只进入手牌/持有区，等待合法窗口；不得通过「立即使用」绕过条件。作为规则解释建议，正式实现前需在规则说明中显式写清。
2. **掘墓人超时存在两个操作节点。** 从两张弃牌中选一张是强制选择；第二步“立即使用还是保留”为可选。依已冻结规则，强制选牌超时应从两张合法候选中随机代选，再默认保留；不能因为超时就不给牌。
3. **反应牌牌权。** 一次攻击最多使用一张已冻结；攻击者被镜僧反杀时，原攻击不能再继续结算死亡；审判者不能引发这两类反应。
4. **隐士牌对象与手牌列表变化。** 只随机查看目标在技能执行瞬间仍持有的合法忍者牌，不从已经打出的牌中偷偷抽取；若目标无牌则按官方实际牌面效果及授权边界单独处理。
5. **身份公开事件的时点。** 记录公开时的身份，交换后旧公开事实不可被当作当前真实身份；公聊猜测不等于官方公开。
6. **首脑只有一张**，正常牌库不存在多个首脑冲突；掘墓人正常初始弃牌至少 4 张，不存在不足两张的常规开局。

### 尚未最终冻结的数字版参数（以下均为推荐值，不擅自变成用户决定）

- 计时器允许的选项：轮抽 **30/45/60/90s**；亮牌 **20/30/45/60s**；技能目标 **15/30/45/60s**；反应 **10/15/20/30s**。默认沿用已冻结的 45/30/30/15。轮间 30s 固定。计时设置只在开局前调整，开局锁定。
- 房主掉线触发管理权转移：**120s**，仅在有在线正式玩家可接管时转移；当前进度、角色和房间密码不变。
- 超时提交与掉线恢复涉及并发先后，以服务端截止时间及单次提交序号决定；每次子步骤均有递增 version，不允许旧提交在后续阶段生效。
- 未冻结的原版疑义：灵媒商人/窃贼没有任意合法荣誉时怎样展示选项；掘墓人取得反应/揭示牌后在合法窗口的保留机制。保守原则：无法满足发动条件则不发动，不自动造牌/加奖。

**待正式冻结项**：上述计时选项、120 秒转移阈值、掘墓人特殊牌的规范文字。若不另作选择，可由用户明确同意推荐后冻结。

### 已确认的主要差距（按优先级）

- **P0 安全/状态**：完整对局离线保留、全员离线暂停及过期清理策略必须联动；不能只让前端倒计时停住而服务端照常结算。
- **P0 保密**：旁观者无私有投影，必须采用单独授权边界。切勿将旁观者添加成普通成员后靠前端隐藏秘密。
- **P0 多阶段推进**：`advance` 当前要求阶段序号改变；复杂技能必须有独立步进版本，每次提交/过期必须做到原子单次结算。
- **P1 房间**：固定人数房间、活动比赛中保留成员、房主失联转移、跨轮内部准备。
- **P1 压测**：4～11 人多端、断线、旁观与聊天高频下，验证状态广播量和历史数据大小，不要复用三人测试就宣称 11 人通过。

### 相容性与保护约束

1. 不替换现有两款游戏引擎；所有新规则、抽牌和奖励都归 Night of Ninja 插件。
2. 公共契约和数据库变更必须兼容已存在旧房间记录，禁止无备份强迁移。
3. 独立本机端口和独立 SQLite 进行测试，不能直接占用线上 3199 或当前活动玩家数据。
4. 本次审查发现原工作树已含大量 P17 网络和 UI 修改，审查不将其视为本轮成果，不自行提交/合并。

## P2 建议实施路线（供后续 Codex 执行，本轮不执行）

### NINJA-P0：规则数据与安全基线

- 确认并冻结剩余的计时范围与房主转移秒数；详细指定掘墓人取得特殊牌时的合法触发规则。
- 以 33 张唯一卡定义 `cardId,phase,number,type,effect`；单轮动态洗牌，带固定随机源进行可复现测试。
- 固定 35 枚荣誉池 `2×14,3×14,4×7`；按无放回随机抽取，补池时增加相同构成，记录公开补池动作；注意所有人可见的仅是标记数不是隐藏分值。
- 定义事件权限级别：public、player-only、authorized-viewers、server-only；快照与回放沿用这些边界。

**门槛**：数据表精确统计 33 张牌、35 枚荣誉；完整规则和默认值可由自动测试重建，旧两款游戏行为无变化。

### NINJA-P1：公共层最小扩展（高风险切片）

- 可选的固定人数条件与游戏专属设置校验；旧插件维持原有最小/最大人数行为。
- 增加不占玩家位的旁观订阅与只公开状态投影；旁观者不许命令、聊天、读取隐藏数据。
- 全体正式玩家离线时暂停对局与计时，恢复剩余时间；从暂停状态恢复后严禁使用失效的墙上时钟截止时间直接跳过多个阶段。
- 正在进行/暂停的比赛免于原有 24h 房间清理策略；兼顾持久化和数据库大小，过期清理必须区别 finished/lobby/activePaused。
- 管理权转移、离线占位、所有玩家退出的语义按插件能力配置，旧游戏仍走既有行为。
- 确认内部多步骤推进可用 `phase` token / 状态版本，不使公共代码无声阻止同阶段多个步骤。

**门槛**：公共层定向测试包括老游戏回归、11 人房间、围观者权限、全员离线 48h 的假时钟、旧 room JSON 恢复、掉线房主转移、重复提交。

### NINJA-P2：纯服务端规则引擎

- 定义比赛状态（整场：玩家/荣誉/获胜者；当前轮：真实身份/已知情报/手牌/弃牌/已出牌/存活/阶段/提交）；服务端为唯一权威源。
- 明确状态推进：`SETUP → DRAFT_ONE → DRAFT_TWO → SPY_COMMIT → SPY_RESOLVE → ... → SHINOBI → HOUSE_REVEAL → AWARDS → ROUND_READY → SETUP/CHAMPION`。技能目标和反应可用子步骤，向外提供单调递增 token。
- 同步轮抽两屏障；同时亮牌/按编号执行；已死亡玩家不可继续正常打牌；选牌/目标超时、可选效果跳过。
- 六种骗徒逐项实现；特别处理变形者的身份与认知分离，掘墓人取得牌、灵媒商人换荣誉、窃贼标记枚数、审判者不可响应。
- 刺杀响应和首脑揭示分离；优先结算当前刺杀响应，再继续牌序。
- 荣誉发奖前检查补池；本轮奖励发完后检查达 10 分、冠军并列、无人生还等边界。
- 事件保存公开/私人记录，并用授权历史快照支持重连。

**门槛**：纯引擎确定性测试覆盖 4/5/7/11 人、全部 13 类牌、阶段交错/反应、身份交换、荣誉与冠军、极端超时和隐私边界。

### NINJA-P3：独立浏览器游戏流程（仅功能版）

- 新建独立 `games/night-of-the-ninja` 的前端操作、规则与房间配置入口，保持公共前端原两款游戏映射不变；此阶段仅基础可操作 UI，不开始美术。
- 玩家可以完成秘密轮抽、同时出牌、查看授权情报、选择目标、反应、查看公开记录与结算；旁观者只有公开状态。
- 为 4～11 人在常见桌面/手机尺寸提供可读操作流程；遵循平台“当前机制高亮、反馈明确”规范，但不落实新美术素材。

**门槛**：至少 4 个完全独立用户会话跑通一整场，多端重连恢复；不允许旁观者或玩家通过网络快照偷看其他人的私人信息。

### NINJA-P4：集成、回归、部署准备

- 测试矩阵：4/5/7/11 人一轮、多人同时提交/超时、完整多轮直到冠军、断线和全离线/恢复、旁观权限、房主转移、补池、服务器重启继续。
- 与《诡吹灯》《骰子狼人杀》原有自动测试及 Playwright 全部回归；3 人游戏不因 11 人支持而改变人数/房间逻辑。
- 使用独立回环端口、独立 SQLite 和隔离 build；依项目现有安全部署规范，核对活动对局后方可考虑正式服务切换。**本阶段仅制定上线检查表，当前不部署。**

### 实施顺序与风险

| 风险 | 等级 | 控制方式 |
|---|---|---|
| 旁观者泄露身份和手牌 | 高 | 服务端公开投影与只读订阅、反向权限测试 |
| 全员离线后时钟快进、删除活动房间 | 高 | 假时钟、持久化恢复与 48h 测试 |
| 同阶段多步骤误结算或重复发奖 | 高 | 全局操作序号、持久化 receipt、回放一致性测试 |
| 改动公共层影响现有两款游戏 | 高 | 增量接口兼容、旧游戏全量回归 |
| 33 张牌和 35 枚荣誉分布出错 | 中 | 数据不变量、种子复现、补池覆盖 |
| 多端 11 人聊天和广播量较大 | 中 | 历史截断/分页、广播规模与网络压力测试 |

**交付顺序**：本文件规则终审与平台审查 → 单独的 Codex 实施 prompt → 公共兼容切片 → 引擎 → 联机功能 UI → 全量验收 → 后续独立美术设计。不得把仅完成方案等同于插件已经实现。
